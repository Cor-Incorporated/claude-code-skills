# プロダクション開発シナリオテスト計画
## CC / Codex / OC 三者比較 — 実プロジェクトでの開発フルサイクル検証
**作成日**: 2026-04-08
**前提**: Dogfooding Report (01) で「プロダクション開発能力が未検証」と判明したことへの対策

---

## 設計思想

前回の Dogfooding 計画はガードレールの発火検証（防御テスト）に偏重していた。
本計画は**攻めのテスト**—つまり「3 ツールが実際の開発作業をどこまで自律的に完遂できるか」を測る。

### 評価する能力
1. **タスク完遂率**: 指示された開発タスクをエラーなく完了できるか
2. **自律修正力**: ビルドエラーやテスト失敗を自分で直せるか
3. **コード品質**: lint, type-check, テストが通るか
4. **時間効率**: 同一タスクにかかるステップ数・所要時間
5. **並列性**: マルチエージェントで分割できるか（Codex / OC のみ）

### 統制条件（前回の反省を反映）
- **モデル統一**: 全ツールで `claude-sonnet-4.5` (OpenRouter) を使用。Codex のみ `gpt-5.4` 固定のため、別枠で記録
- **実行モード統一**: 全ツール TUI（対話モード）で実行。`claude -p` は使わない
- **状態リセット**: 各シナリオ前に `reset-state.sh` + `git checkout -- .`
- **ブランチ戦略**: 各シナリオごとに `test/scenario-{id}-{tool}` ブランチを作成

## テストシナリオ

### シナリオ 1: バグ修正フルサイクル（プロジェクト B）
**難易度**: ★★☆ (中)
**推定所要時間**: 各ツール 20-30 分

**プロンプト（3 ツール共通）**:
```
engineer-cafe-navigator2025 の backend/agents/ にある voice_agent.py で、
TTS レスポンスのタイムアウト処理が不十分です。
タイムアウト時に適切なフォールバックメッセージを返すように修正し、
テストを追加してください。
修正が完了したら、ブランチを作成して PR を作ってください。
```

**評価基準**:
- [ ] ソースコードの変更が正しいか（タイムアウト処理の追加）
- [ ] テストが追加されているか
- [ ] テストが通るか (`pytest`)
- [ ] lint が通るか
- [ ] ブランチ作成 → コミット → push → PR 作成のフルサイクル完了
- [ ] PR の description が適切か

**記録項目**: 完了(Y/N), ステップ数, エラー遭遇数, 自律修正数, 所要時間

### シナリオ 2: 新規 API エンドポイント追加（プロジェクト A）
**難易度**: ★★★ (高)
**推定所要時間**: 各ツール 30-45 分

**プロンプト（3 ツール共通）**:
```
BenevolentDirector の services/control-api に新しい
GET /api/v1/health/detailed エンドポイントを追加してください。
このエンドポイントは以下を返します:
- データベース接続状態
- Pub/Sub 接続状態
- LLM Gateway の到達性
- サービスのアップタイム
packages/contracts/openapi.yaml も更新してください。
テストも追加してください。
```

**評価基準**:
- [ ] Go のエンドポイント実装が正しいか
- [ ] OpenAPI spec が更新されているか（contract-first 遵守）
- [ ] Go テストが追加されているか
- [ ] `go build` が通るか
- [ ] `npm run ci:v2:openapi` が通るか（OpenAPI ガードレール）
- [ ] ブランチ → PR のフルサイクル完了

### シナリオ 3: TDD サイクル（プロジェクト A）
**難易度**: ★★★ (高)
**推定所要時間**: 各ツール 30-45 分

**プロンプト（3 ツール共通）**:
```
BenevolentDirector の services/intelligence-worker に新しいユーティリティ
`retry_with_backoff` を TDD で実装してください。
1. まずテストを書く（RED）
2. 最小限の実装でテストを通す（GREEN）
3. リファクタリングする（REFACTOR）
仕様:
- 最大リトライ回数、初期遅延、バックオフ倍率を引数に取る
- 指数バックオフ + ジッター
- 特定の例外クラスのみリトライ対象
```

**評価基準**:
- [ ] RED フェーズ: テストが先に書かれたか
- [ ] GREEN フェーズ: 最小実装でテストが通ったか
- [ ] REFACTOR フェーズ: コード品質が改善されたか
- [ ] 最終テストカバレッジ
- [ ] `pytest` が全て通るか

### シナリオ 4: モノリポ横断変更（プロジェクト A）
**難易度**: ★★★★ (非常に高)
**推定所要時間**: 各ツール 45-60 分

**プロンプト（3 ツール共通）**:
```
BenevolentDirector に新しいイベント "project.handoff_requested" を追加してください。
変更が必要な箇所:
1. packages/contracts/openapi.yaml にイベントスキーマを追加
2. packages/domain-events/ にイベント定義を追加

4. services/intelligence-worker/ でサブスクライブ
5. 関連する ADR ドキュメントを作成
全ての変更に対してテストを書いてください。
```

**評価基準**:
- [ ] 5 箇所すべてに変更があるか
- [ ] 変更間の整合性（型名、イベント名、スキーマの一致）
- [ ] Go / Python / YAML の 3 言語を正しく扱えたか
- [ ] CI ガードレール (`ci:v2:openapi`, `ci:v2:schema`, `ci:v2:monorepo`) が通るか
- [ ] ADR が適切に書かれているか

## スコアリング

### シナリオごとのスコア（各 20 点満点）

| 項目 | 配点 |
|------|------|
| タスク完了 | 5 点（完了=5, 部分=2, 未完了=0）|
| テスト合格 | 4 点（全通過=4, 一部=2, なし=0）|
| コード品質 | 4 点（lint+type通過=4, 警告あり=2, エラー=0）|
| 自律修正力 | 4 点（全エラー自己修正=4, 一部=2, 手動介入必要=0）|
| 効率 | 3 点（最少ステップ=3, 平均=2, 冗長=1）|

## 実施手順

### 事前準備（30 分）
1. 全ツールのモデルを `claude-sonnet-4.5` に統一（Codex は gpt-5.4 固定で別枠記録）
2. テスト用ベースブランチを develop から作成
3. 各プロジェクトの CI が通る状態を確認
4. reset-state.sh の実行確認

### 実施順序（推定 4 時間）
1. シナリオ 1（バグ修正）: CC → Codex → OC（各 25 分 + リセット 5 分）= 90 分
2. シナリオ 2（API 追加）: CC → Codex → OC（各 40 分 + リセット 5 分）= 135 分
3. シナリオ 3（TDD）: OC のみ先行テスト = 40 分（残りは時間に応じて）
4. シナリオ 4, 5: 時間に応じて実施

### 記録
- 各シナリオの開始・終了時刻
- ツールの出力ログ（スクリーンショットまたは `script` コマンド）
- git diff の保存（`git diff > scenario-{id}-{tool}.patch`）
- CI 実行結果
