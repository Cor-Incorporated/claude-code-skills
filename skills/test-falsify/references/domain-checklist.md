# ドメイン別テスト整合性チェックリスト

> **設計方針**: このチェックリストはプロジェクト非依存。
> 各ドメインの「入力を変えたら出力も変わるべき」という普遍原則を具体化したもの。
> プロジェクト固有の閾値や用語は SKILL.md の Phase 3 で調整する。

---

## 対話システム / チャットボット / インタビュー

### 赤信号パターン（均一性 = バグ）

- [ ] 入力内容に関係なくターン数が同じ → 入力を評価していない
- [ ] 全モデル/全設定で結果が完全一致 → 回数消化型の機械的動作
- [ ] 情報量の多い入力でも処理ステップ数が減らない → 早期終了ロジックなし
- [ ] 終了シグナル（「もういい」「なし」等）を送っても処理が続く → ユーザー意図を無視

### 期待される変動パターン

- 詳細な入力 → 少ないステップで目標到達 → 短い会話
- 短い入力 → ステップ上限まで消化 → 長い会話
- モデル/設定差 → 応答品質が異なる → ステップ数にばらつき

### 必須テストケース

1. **変動テスト**: 異なる入力パターン（詳細/簡潔/混合）で結果が変動するか
2. **上限テスト**: 設定上限を超えないか
3. **早期終了テスト**: 目標充足で処理が短縮されるか
4. **中断テスト**: 終了シグナルで適切に停止するか

## 推薦 / パーソナライズシステム

### 赤信号パターン

- [ ] ユーザープロファイルに関係なく同じ推薦結果
- [ ] 行動履歴を変えても推薦順位が変わらない
- [ ] コールドスタートとウォームスタートで同じ結果
- [ ] A/Bテスト群間で結果が同一

### 期待される変動パターン

- 異なるユーザー属性 → 異なる推薦リスト
- 行動履歴の蓄積 → 推薦精度の向上（順位変動）
- 新規ユーザー → 汎用推薦 / 既存ユーザー → パーソナライズ推薦

## 検索 / ランキングシステム

### 赤信号パターン

- [ ] クエリを変えても同じランキング
- [ ] ブースト/ペナルティが反映されない
- [ ] ファセットフィルタが結果に影響しない
- [ ] ページネーションで全ページ同一結果

### 期待される変動パターン

- 異なるクエリ → 異なるランキング
- フィルタ適用 → 結果セットの絞り込み
- ブースト設定変更 → 順位の変動

## 生成AIシステム

### 赤信号パターン

- [ ] プロンプトに関係なく同じ出力長
- [ ] temperatureを変えても出力が同一
- [ ] 制約条件を変えても出力が変わらない
- [ ] 異なるモデルで完全同一の出力

### 期待される変動パターン

- 詳細なプロンプト → より具体的な出力
- temperature上昇 → 出力の多様性増加
- 制約追加 → 出力形式の変化

## CRUD / データ処理システム

### 赤信号パターン

- [ ] 異なる入力データで同じバリデーション結果
- [ ] フィルタ条件を変えても同じ件数が返る
- [ ] ソート指定を変えても順序が同じ
- [ ] ページサイズを変えてもレスポンスサイズが同じ

### 期待される変動パターン

- 有効/無効入力 → バリデーション通過/拒否
- フィルタ条件変更 → 結果件数の変動
- ソート指定変更 → 順序の変動

## 認証 / 認可システム

### 赤信号パターン

- [ ] 異なる権限レベルで同じアクセス結果
- [ ] 無効トークンでも認証成功
- [ ] レート制限設定を変えても同じ挙動
- [ ] 異なるロールで同じリソースにアクセス可能

### 期待される変動パターン

- 有効/無効認証情報 → 成功/失敗
- 異なる権限レベル → アクセス可能リソースの差異
- レート超過 → 429エラー

## 金融 / 決済システム

### 赤信号パターン

- [ ] 異なる金額で同じ手数料
- [ ] 通貨を変えても同じ換算結果
- [ ] 割引コード適用前後で同じ合計金額
- [ ] 異なる税率地域で同じ税額

### 期待される変動パターン

- 金額変動 → 手数料の比例変動

- 割引適用 → 合計金額の減少

## データパイプライン / バッチ処理

### 赤信号パターン

- [ ] 入力データ量に比例しない処理時間
- [ ] 異なるデータソースで同じ出力件数
- [ ] エラーレコードを含むバッチと含まないバッチで同じ成功率
- [ ] 並列度を変えてもスループットが同じ

### 期待される変動パターン

- データ量増加 → 処理時間の増加（線形またはサブリニア）
- エラーレコード混入 → 成功率の低下
- 並列度変更 → スループットの変動

## 共通チェック項目

### 下限チェックだけでは不十分なケース

```
❌ assert result >= MIN_THRESHOLD  # バグ値がMINを超えていればパス
✅ assert MIN_THRESHOLD <= result <= MAX_THRESHOLD  # 範囲チェック
✅ assert abs(result - expected) < tolerance  # 許容誤差チェック
✅ assert len(set(results)) > 1  # 変動チェック
```

### E2E結果報告時の必須確認

1. 結果の分布（min, max, mean, stddev）を計算
2. stddev ≈ 0 の場合は「安定」ではなく「機械的」として報告
3. ドメイン固有の期待分布と照合

### 汎用の反証テストパターン

```python
# パターン1: 入力変動 → 出力変動の検証
results = [run(input_a), run(input_b), run(input_c)]
values = [extract_metric(r) for r in results]
assert len(set(values)) > 1, "異なる入力で同じ結果 = 入力を無視している"

# パターン2: 範囲チェック（上限+下限）
assert LOWER <= metric <= UPPER, f"範囲外: {metric}"

# パターン3: 設定変更の反映確認
result_default = run(config=default)
result_modified = run(config=modified)
assert result_default != result_modified, "設定変更が反映されていない"
```
