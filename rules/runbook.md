# 手順書・運用文書のルール

## 発端（2026-07-27 のインシデント）

Alpha デプロイ手順書を 2 度書き、2 度とも**実行不可能**だった。

- `plan_run_id` / `plan_sha256` を「成功した plan run の値を入力」とだけ書き、取得方法を書かなかった
- 必須の前提である `ALPHA_SOURCE_SHA`（`dev-terraform` environment）の更新を**丸ごと欠落**させた。この変数は「develop head と完全一致」が強制されるため、飛ばすと plan が必ず失敗する
- 同じ欠陥をリポジトリの正本 runbook (`docs/v2/alpha-operations-runbook.md`) にも書き込んでいた（`ALPHA_SOURCE_SHA` の出現回数 0）

**なぜ起きたか**: ワークフロー定義を読まず、過去に人間が実行するのを見ていた記憶から書いた。文書は番号付きの手順・警告・検証コマンドを備えて**完成して見えた**ため、値が無いことに気づけなかった。

**最も重い問題**: コードには反証を要求していたのに、人間が実際に実行する文書には検証を一切しなかった。**壊れたテストは自分の CI で落ちるが、壊れた手順書は相手が作業を始めた後に落ちる。** コストを相手に外部化した。

---

## 必須ルール

### 1. 実値主義 — 「〜の値を入力」は禁止

手順書に現れる入力欄は、次のいずれかでなければならない。

- **実際の値が書いてある**（`36902d5bb5c655b733f06311539237ff5f222b90`）
- **値を取得するコマンドが書いてある**（コピペで動くもの）
- **「空欄のまま」と明記されている**

「成功した run の値を」「適切な SHA を」のような**参照だけの記述は欠陥**とみなす。

### 2. 定義ファイルから機械的に列挙する

記憶・過去の会話・既存文書からは書かない。**必ず定義を読む。**

- GitHub Actions: `workflow_dispatch.inputs` の全項目と `required` / `default`
- **`vars.*` / `secrets.*` / env 経由の外部依存も列挙する**（inputs 欄に出ないので最も漏れやすい）
- スクリプト: 引数と必須環境変数

### 3. 現在値と設定値を並べる

変更が必要な変数は「**現在値 → 設定する値**」の形で書く。現在値は実測する。

これがあれば「もう設定済みか」が判断でき、二重実行を防げる。

### 4. 相手に渡してよいのは「CLI で実行不可能なもの」だけ

**基準は「本番かどうか」ではない。「自分が実行できるかどうか」である。**

| 判定 | 扱い |
|---|---|
| **CLI で実行できる**（`gh workflow run`、`gh variable set`、`gcloud`、API） | **自分でやる。例外なし。** production の apply / deploy であっても渡さない |
| **CLI で実行不可能**（ブラウザ UI 必須、対話ログイン、物理操作、人間の目視判断） | 相手に依頼する。ただし**値は全て埋めて渡す** |

`gh workflow run` は `workflow_dispatch` の全ワークフローを起動できる。**したがって GitHub Actions のワークフローは、production deploy であっても「渡してよいもの」ではない。**

**「production だから人間が」は自分の勝手な分類であって、相手のルールではない。** 実行可能性で判断する。

「手順書を書く」ことと「作業を渡す」ことは同じではない。**渡す前に、渡す必要が本当にあるかを問う。**

### 5. 実行者テスト（書き終えたら必ず）

> **この文書だけを見て、この作業を見ていない人が実行できるか。**

できない箇所を具体的に指摘し、潰す。「たぶん分かるだろう」は不可。

### 6. バリデーションから失敗モードを逆算する

定義ファイルの正規表現・CHECK 制約から、起こりうる入力ミスを先回りして「問題が起きたら」表に入れる。

例: `^[0-9a-f]{64}$` → バッククォート混入・大文字混入・改行混入

---

### 7. 秘密の登録は「検証 → 登録 → 削除」を 1 つのコマンドにして渡す（2026-10-31 のインシデント）

cor-os の `CLOUDFLARE_ACCESS_READ_API_TOKEN` の登録に 5 回・約 50 分かかり、無効な値が 2 回 GitHub secret に入った。

- 手順は旧い UI の文言と、token の長さ（40 文字の決め打ち、実物は 53 文字）を、実物を見ずに書いていた。
- コピーと貼り付けの順番を人に委ねていた。
- verify が通らなくても登録まで走る 1 行を渡していた。

- 渡すのは `bash ~/.claude/scripts/register-secret-verified.sh <NAME> <owner/repo> --verify-url <URL>`（Cloudflare なら `--cloudflare-account <id>`。id は `wrangler whoami` の 32 桁）。値は表示しない入力で受け、verify が通ったときだけ登録する。script を通さない登録コマンドを手順に書かない（`tests/test-handover-secret-steps.sh`）。
- UI 操作は、スクショか実機で確かめた文言だけを書く。確かめていないものは「未確認」と書く。
- 値の形式（長さ・文字種）を決め打ちしない。形式は提供元の verify が決める。

## チェックリスト（手順書を出す前に）

- [ ] ワークフロー/スクリプトの**定義ファイルを開いて読んだ**
- [ ] `inputs` を全項目列挙した（`required` と `default` 付き）
- [ ] **`vars.*` / `secrets.*` / env の外部依存を列挙した**
- [ ] 全ての入力欄が「実値」「取得コマンド」「空欄と明記」のいずれか
- [ ] 変更する変数は「現在値 → 設定値」で書いた
- [ ] **自分で実行できるステップを相手に渡していない**
- [ ] 実行者テストを通した
- [ ] 秘密の登録は `register-secret-verified.sh`（検証 → 登録 → 削除）で渡した。UI の文言は確かめたものだけ
- [ ] バリデーションから失敗モードを逆算した

# 宣言と実体の二重管理

## 発端（同じ日に 3 回起こした）

同じ事実が「宣言的な設定」と「実際に強制するコード」の 2 箇所にあり、**片方だけ更新して壊した。**

| # | 宣言側（更新した） | 実体側（見なかった） | 結果 |
|---|---|---|---|
| 1 | workflow の `inputs` | `vars.ALPHA_SOURCE_SHA` | 手順書が実行不可能 |
| 2 | `MAX(evidence_grade)` を書いた | sqlmock は SQL を評価しない | ガードレールが反証を検出できず |
| 3 | `grift-deployment-policies.json` の許可版数 | `alpha_migration_preflight.go` のハードコード | **Alpha CD 停止** |

3 は migration 000055 の時点で既に漏れており、**次のデプロイで必ず出る潜在バグ**だった。

## ルール

### A. 設定値を変えたら「誰が強制しているか」を必ず探す

宣言ファイルを編集したら、**その値を実際に読んで判定しているコードを grep する。** 設定を変えただけで動作が変わると仮定しない。

```bash
# 例: 許可バージョンを変えたら
grep -rn "allowed_pre_migration_versions" --include="*.go" --include="*.mjs" --include="*.py" .
grep -rnE "MigrationVersion = [0-9]+" --include="*.go" .
```

### B. 同じ事実が 2 箇所にあるなら、機械的に結ぶテストを書く

コメントで「keep in sync」と書くのは**対策ではない**。**片方を変えたら落ちるテスト**を書く。

```go
// 宣言ファイルを実際に読んで定数と比較する
func TestConstantsMatchPolicyFile(t *testing.T) { ... }
```

そのテストは**両方の値を挙げて失敗する**こと。「不一致」だけでは直せない。

### C. エラーメッセージに観測値を入れる

期待値だけを出すメッセージは診断に使えない。

```
悪い: Alpha schema must be exactly clean version 49 or 54
良い: Alpha schema must be clean and one of [49 55 56] (observed 55, dirty=false)
```

### D. 定数をバージョンで pin しているテストを疑う

`AcceptsV54Boundary` のように**版数を名前と値に焼き込んだテスト**は、移行のたびに古い版を pin し続ける。**定数参照に変える。**

## 原則

**手順書は実行可能成果物である。コードと同じ検証を要求する。**

コードに反証を求めるなら、手順書にも「この文書で実行できるか」の検証を求める。**構造的な完成度は正しさではない。** 番号付きの手順と警告と検証コマンドが揃っていても、値が 1 つ欠ければ実行できない。

そして**その失敗は相手の時間で起きる。**
